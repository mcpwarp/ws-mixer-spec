# Client SDK requirements

Status: **normative**, language-independent by construction. These are behavioural requirements for
**every** `ws-mixer.v1` client SDK — JS, Python, a Go client, or any future one. They are stated once here
so a new SDK has a checklist independent of any one language's implementation.

Wire-level behaviour (framing, streams, flow control, control messages, error codes) is defined in
[`WIRE.md`](./WIRE.md); this document only adds the client-side behavioural obligations that sit above the
wire and are not implied by it alone.

| Requirement | Rule |
|---|---|
| Reconnect / backoff | Exactly the state machine in [WIRE.md §2.9](./WIRE.md#29-sequences) "Reconnect" — full-jitter backoff, `attempt` resets only once a connection has been **stable** (`stable`, default 10 s past that connection's own `welcome`) — this timer belongs to one connection, so a drain hand-over's old connection closing never cancels the new connection's timer — drain/`4012` handling, fatal-close handling. Not restated here; implement that table. |
| Token provider | `token` MAY be a static string or a callback returning a fresh token (sync or `Promise`). The callback MUST be invoked on **every** dial, not cached across reconnects. |
| Rejected token | A token can be rejected in two places before `welcome`: HTTP `401` on the upgrade, or `error{UNAUTHORIZED}` / close `4011` after the 101. Both get the **same** treatment: when `token` is a provider (callback), the SDK calls it **once more** and retries the dial **immediately** (no backoff); a second rejection (either form) is fatal. The one-refresh budget re-arms only once a connection has been stable (the Reconnect/backoff row's `stable`), not on `welcome`. When `token` is a static string there is nothing to refresh, so the **first** rejection is fatal — no retry, no backoff loop: the same token cannot start working, and retrying forever hammers the auth service and hides the real problem from the user. A `4011` received **after** `welcome` is outside this row's scope and stays fatal exactly as before — see [WIRE.md §2.9](./WIRE.md#29-sequences). If the provider's call on this one refresh-retry fails with the marked-temporary signal below, the refresh budget is still spent — it does not get a second attempt — and the failure takes the ordinary recoverable path the Provider failure row describes for a marked failure. |
| Provider failure | A provider that throws or rejects on a dial's initial call is normally **fatal**: no retry, the thrown/rejected error surfaced verbatim to the caller. A provider MAY instead signal that a given failure is **temporary** — the token itself isn't the problem, it just couldn't be obtained right now (e.g. the network is briefly down, or the auth server is unreachable while refreshing an expired token) — through an explicit, SDK-defined marker: Go, an exported sentinel `ErrTokenUnavailable` the provider's error wraps, matched with `errors.Is`; JS, an exported `TokenUnavailableError` class. This is opt-in only: an SDK MUST NOT infer "temporary" from the shape of an arbitrary error (no duck-typing a `retryable` property or method) — an accidental match would turn a genuinely fatal provider failure into an endless retry loop. A marked failure is treated exactly like a failed dial — `phase: "dial"`, `fatal: false`, normal backoff (it counts as a failed attempt: `attempt` increments, the stability rule applies as for any other failure, a bounded retry count still applies) — with no immediate retry, the provider's error surfaced verbatim as the disconnect reason's cause. See [WIRE.md §2.9](./WIRE.md#29-sequences)'s Reconnect table. An unmarked provider failure stays fatal exactly as before, on either the initial call or the one refresh-retry call in the Rejected token row above. |
| Disconnect reason shape | Every disconnect (recoverable or fatal) is reported as one object carrying: `phase` (`"dial"` \| `"handshake"` \| `"connected"`), `wsCode` when a WS close occurred, `errorCode`/`errorName`, `httpStatus` when the upgrade itself failed, `fatal: boolean`, a human-readable `message`, and `closeReason`. `phase` is `"dial"` up to and including the HTTP upgrade response, `"handshake"` from the 101 until `welcome`, and `"connected"` from `welcome` onward. `errorCode`/`errorName` are present from four sources, and never otherwise: (1) a peer's `error` message that preceded the close — they are that message's code/name (which for a `code > 999` differs from the clamped `4002` on the wire — see the `wsCode` row); (2) a close frame with a ws-mixer code in `4001`–`4999` observed with **no** preceding `error` (a bare close) — the SDK derives them mechanically, `errorCode = wsCode - 4000`, `errorName` from the [WIRE.md §2.8](./WIRE.md#28-error-codes) table (unknown → `INTERNAL_ERROR`, as everywhere), since that derivation cannot be wrong and a name is more useful to the application than nothing; (3) a ws-mixer error the SDK itself raises locally, with no close frame from the peer at all — the welcome timeout (`PROTOCOL_ERROR`, the Handshake-phase close row's locally generated `4001`), any other local protocol-violation failure of the connection, and a missing or mismatched subprotocol echo on the upgrade, which the SDK classifies `UNSUPPORTED` (the Fatal set row's `4010`) even though there is neither a close code nor an HTTP status to derive it from; (4) the SDK's own call to the Application close row's API — `errorCode` is the caller's own code, `errorName` is `APPLICATION_CLOSE`. `errorCode`/`errorName` are **never** synthesised for anything that isn't a ws-mixer code: an HTTP upgrade rejection is reported through `httpStatus` alone (not, e.g., labelled `UNAUTHORIZED`), and an abnormal closure (`1006` / no close frame at all) or any other non-ws-mixer close code (`1000`, `1001`, `1009`, `1011`, …) carries no `errorCode`/`errorName`. |
| `wsCode` | When derived from a ws-mixer `error` this side is closing on (its own caller's code or a peer's), it is the semantic `4000 + code` — even for a `code > 999`, where [WIRE.md §2.8](./WIRE.md#28-error-codes) requires the wire itself to carry the clamped `4002` instead. When observed from a bare close frame (no preceding `error` this side generated), it is exactly what was on the wire — and if it falls in `4001`–`4999`, the Disconnect reason shape row's `errorCode`/`errorName` are derived from it. When no close frame was received at all, it is whatever the library reports for an abnormal closure (typically `1006`) or absent — an SDK MUST NOT fabricate a ws-mixer code for a close that never happened. (The welcome timeout's `4001` is not fabricated: that close is one the client itself sends.) |
| `closeReason` | The reason field of the close frame **received from the peer** — never the SDK's own outgoing reason. It is the bytes as received (at most 123 UTF-8 bytes) — the SDK MUST NOT re-truncate or normalise them. If the underlying library surfaces a reason that is not valid UTF-8, the SDK SHOULD surface a lossy (U+FFFD) decoding rather than drop the field, and MUST NOT treat the bad encoding itself as fatal. SHOULD rather than MUST because some libraries reject an invalid-UTF-8 close frame outright before the SDK ever sees the bytes; that disconnect is then reported as whatever the library surfaces — typically `wsCode: 1007`, or `1006` (abnormal closure) when the library tears the connection down without completing the close handshake — and no `closeReason`. Absent or empty whenever no reason was received from the peer — including when this side initiated the close (a peer's echo carries no information and RFC 6455 doesn't require it to copy the reason), and when the SDK closed on `error` without reading the close frame that followed it, as [WIRE.md §2.7](./WIRE.md#27-control-channel-stream-0) allows ("logs, surfaces and closes"); the human-readable text is then in `message` instead. Consumers SHOULD prefer `closeReason` and fall back to `message`. |
| Handshake-phase close | Both a close frame observed between the 101 upgrade and `welcome`, and the client's own 10 s welcome timeout ([WIRE.md §2.9](./WIRE.md#29-sequences)), are reported with `phase: "handshake"` — not as a dial failure. A received close carries the peer's `wsCode`, and its `closeReason` when the close frame itself was read (see the `closeReason` row). The welcome timeout carries the locally generated `wsCode: 4001` and no `closeReason` (nothing was received from the peer). **Any other failure** in this window — transport death with no close frame, an unreadable frame — is `phase: "handshake"` too, with `wsCode` as the `wsCode` row above describes for "no close frame at all". A connect the application itself cancels in this window is not a handshake failure. |
| Application close | The SDK MUST expose a connection-close API taking a ws-mixer error code and message, so the application can close with `APPLICATION_CLOSE` (`0x0e` / 4014). The SDK performs [WIRE.md §2.8](./WIRE.md#28-error-codes)'s three steps: `error{code:14, message}` on stream 0, WS close `4014` with the message truncated to 123 UTF-8 bytes on a character boundary, then close the socket. On an SDK with an automatic reconnect loop, this API MUST also stop that loop — the client closes and stays closed, reporting one non-fatal disconnect — so it cannot be implemented by closing the underlying connection behind the reconnect loop's back. |
| Fatal set | From [WIRE.md §2.9](./WIRE.md#29-sequences): close `4010`; HTTP `403`, HTTP `404`; missing subprotocol echo — always fatal. Close `4011` and HTTP `401` per the Rejected token row above: fatal immediately for a static token, fatal after the one refresh-retry for a provider, and unconditionally fatal when `4011` arrives after `welcome`. Also fatal: an unmarked token-provider failure (see above — a marked temporary failure is not fatal; it takes the recoverable dial path instead), and — for an SDK that offers a bounded retry count `N` — reconnect attempts exhausted: it counts the same `attempt` [WIRE.md §2.9](./WIRE.md#29-sequences) defines (consecutive reconnects since the last stable connection), and goes fatal when the `N`th such reconnect fails, exactly like an SDK that never connects at all. How "unlimited" and "no reconnect at all" are each expressed is SDK-defined, not normative here. |
| Handler delivery | Stream, `app`, and `drain` handlers are delivered in wire order from **one** delivery loop per connection, and never concurrently with each other or with themselves — a slow handler must not reorder or overlap deliveries. An event that has already been received when the connection ends is still owed to its handler: `error` is the last message on the wire ([WIRE.md §2.7](./WIRE.md#27-control-channel-stream-0)), so a stream `OPEN`, `app` or `drain` queued ahead of it arrived before the connection ended and MUST still be delivered — the delivery loop drains what it already holds rather than discarding the backlog. An SDK MAY therefore invoke a handler shortly after its own close/teardown call has returned. |
| Stream teardown on disconnect | When the connection ends for any reason other than that stream's own clean `CLOSE` — including an abnormal closure with no close frame at all — every stream still open MUST end with an error visible to its reader/writer, never as a clean end-of-stream; a read or write pending, or started afterward, MUST fail promptly rather than hang. Data already buffered and a `CLOSE`/`RESET` already received for that stream are still delivered first — [WIRE.md §2.5](./WIRE.md#25-streams)'s "CLOSE preserves buffered data; RESET discards it" is unaffected by how the connection itself ends. |
| Stats / counters | The "ignore and count" counters (unknown frame types, stale frames, duplicate pongs, refused opens, protocol violations, bytes in/out) MUST be exposed via some accessor on the client (each SDK documents its own shape — e.g. the JS SDK's `client.stats()`). |

Each language's own implementation notes (WebSocket library choice, exposed types, usage examples) live in
that SDK's own repo — see [`REPOS.md`](./REPOS.md) for the map.
