# ws-mixer spec artifacts

Normative source: [`../docs/WIRE.md`](../docs/WIRE.md). Where anything here and WIRE.md
disagree, WIRE.md wins — everything below is derived from it, not the other way around.

## Layout

```
spec/
  control.schema.json          JSON Schema draft 2020-12, strict, one $defs entry per control message type
  control.relaxed.schema.json  generated: strict minus every additionalProperties:false. Never hand-edited
  fixtures/
    COUNTS.json                      checked-in floor for the total fixture count (see Validation below)
    control/<type>/valid/*.json      one directory per t: hello, welcome, ping, pong, drain, error, app
    control/<type>/invalid/*.json
    control/envelope/invalid/*.json  envelope-level violations that aren't any one message type (see below)
    frames/*.json                    hex-encoded mux frame corpus (wire format, WIRE.md section 2.2-2.4)
    sequences/*.json                 named connection transcripts + expected terminal state
  tools/
    gen-relaxed-schema.mjs    (re)generates control.relaxed.schema.json from control.schema.json
    check-fixtures.mjs        validates every fixture against control.schema.json /
                               control.relaxed.schema.json and re-derives every frame fixture's
                               `decoded` from its `hex`, dependency-free
```

**Deliberate deviation from the original design sketch:** an earlier plan showed one flat
`fixtures/hello.json welcome.json ping.json ...` file per message type. In practice each type needs
several valid and several invalid cases (see "Control message fixtures" below), so this repo nests them
one directory per type with `valid/`/`invalid/` subdirectories instead of one file per type; nothing here
contradicts the wire spec itself, only where the fixture *files* live on disk.

## `control.schema.json`

Draft 2020-12. Top level is a `oneOf` over 7 `$defs` entries (`hello`, `welcome`, `ping`, `pong`, `drain`,
`error`, `app`), each with its own `$id`, `title`, `description`, `required`/optional fields matching
WIRE.md section 2.7's field tables exactly. `t` is a `const` discriminator in every def.

**This schema is strict by design** (`additionalProperties: false` on every object except `meta` and
`body`). That is deliberately
stricter than the wire: WIRE.md section 2.7's forward-compatibility rule says an unknown *field* on a
known `t` is ignored at runtime. The two are reconciled by treating this schema for what it is: **a
test-time-only conformance oracle**, used to catch field-name
typos (`max_stream` vs `max_streams`) during development and CI. It is never linked into a production SDK.
A real implementation's runtime path validates with hand-written, per-field checks (a `switch`/`match` on
`t`, then explicit checks) — never a JSON Schema validator on the hot path, and never against the top-level
`oneOf` even in tests (a bad `ping` would report "must match exactly one schema in oneOf" plus 7 sub-error
groups, which is exactly the unhelpful error this spec exists to eliminate — dispatch on `t` first).

One exception to the "always strict" rule beyond `meta`/`body`: `drain.reason` is intentionally typed as a
free-form string, not a closed `enum`, because WIRE.md section 2.7 explicitly says an unrecognized
`reason` is tolerated at runtime ("treat as maintenance and count"), unlike an unrecognized field name or
an unrecognized `t`. See `fixtures/control/drain/valid/unknown_reason_tolerated.json`.

## `control.relaxed.schema.json`

Generated by `tools/gen-relaxed-schema.mjs` from `control.schema.json`: every `additionalProperties: false`
is stripped, nothing else changes. This is the schema that actually models **wire validity** — an unknown
field on a known `t` is tolerated here, matching WIRE.md section 2.7's runtime forward-compatibility
rule, whereas `control.schema.json` deliberately rejects it as a development-time typo-catcher (see above).
**Never hand-edit this file.** Regenerate it with `node spec/tools/gen-relaxed-schema.mjs` whenever
`control.schema.json` changes, and commit the result — `check-fixtures.mjs` fails the build if the checked-in
file has drifted from a fresh generation.

**SDK runtime validators assert `wire_valid`; schema/CI tooling asserts `schema_valid`.** Concretely: a
production SDK's hand-written per-field validator should agree with `control.relaxed.schema.json`
(`wire_valid`), because that is what the wire actually tolerates; `control.schema.json` (`schema_valid`) is
consulted only by this repo's own CI and by a test suite deliberately checking for field-name typos.

## Control message fixtures

`spec/fixtures/control/<type>/{valid,invalid}/*.json`, one file per case:

```json
{
  "description": "human-readable summary of what this fixture exercises",
  "message": { "...": "the control message object itself, exactly as it would appear as stream-0 DATA payload" },
  "schema_valid": true,
  "wire_valid": true,
  "expect": { "error_code": "SOME_CODE", "message_contains": "..." }
}
```

A fixture now carries two independent booleans instead of one `valid`:

- **`schema_valid`** — does the message validate against the strict `control.schema.json`? This is the
  development-time typo-catcher; it rejects unknown fields even though the wire tolerates them.
- **`wire_valid`** — does the message validate against `control.relaxed.schema.json`, i.e. is it actually
  legal on the wire per WIRE.md section 2.7? This is what a real SDK's runtime validator should agree
  with.

For almost every fixture the two agree (`true`/`true` or `false`/`false`). The one place they diverge is an
otherwise-well-formed message carrying an extra, unrecognized field: `schema_valid: false` (the strict
schema's `additionalProperties: false` catches it) but `wire_valid: true` (WIRE.md section 2.7's
forward-compatibility rule tolerates it at runtime) — see
`fixtures/control/{app,hello}/invalid/unknown_top_level_field.json` and
`fixtures/control/pong/invalid/unknown_field.json`.

`expect` is present only when `schema_valid` is `false`, and is a hint for a human debugging a failure, never
something to assert equality against (fixture discipline in the research docs: assert on `schema_valid` /
`wire_valid`, never on exact error text). `error_code` is one of the names from WIRE.md section 2.8's
table.

Every one of the 7 message types has at least one `schema_valid` fixture and at least three fixtures with
`schema_valid: false`, and coverage spans: a missing required field, a wrong-typed field, an unknown `t`
value, an unknown/extra field, boundary values (window, ping id, deadline, stream id), empty `meta`/`body`
objects, and unusual-but-well-formed capability strings. `check-fixtures.mjs` enforces this coverage rule
per type and hard-fails if a type's `valid/`/`invalid/` directory is missing outright.

### `control/envelope/invalid/*.json`

Envelope-level violations aren't about any *one* message type — they're about the JSON envelope stream-0
DATA payload arrives in, before dispatch on `t` even happens (WIRE.md section 2.7's envelope table):
a non-object array, a bare scalar, an object missing `t`, an object whose `t` isn't a string, and JSON that
doesn't parse at all. This directory holds those five cases. It has no `valid/` sibling (there is no such
thing as a "valid envelope" fixture separate from a valid message of some type) and is therefore exempt from
the "≥1 schema_valid per type" rule above, though it still must carry ≥3 fixtures like every other bucket.

`malformed_json.json` is the one fixture in the entire `control/` tree that cannot carry a `message` field at
all — the point is that the bytes never parse as JSON in the first place. It carries a `raw` string (the
literal, deliberately-broken JSON text) instead, and `check-fixtures.mjs` asserts `JSON.parse(raw)` throws.

## Frame fixtures

`spec/fixtures/frames/*.json`, one file per case, wire format per WIRE.md section 2.2 (8-byte big-endian
header: 1B `type`, 1B `flags`, 2B `reserved`, 4B `stream_id`, then payload):

```json
{
  "description": "...",
  "hex": "lowercase hex, no spaces, header + payload concatenated",
  "valid": true,
  "decoded": { "type": "DATA", "flags": 0, "stream_id": 1, "payload_hex": "..." },
  "expect": null
}
```

For invalid frames, `decoded` is `null` and `expect` is `{ "error_code": "...", "connection_fatal": true|false }`
— `connection_fatal: false` marks a stream-scoped violation (e.g. `WINDOW` increment of 0), `true` marks one
that kills the whole connection. Some `decoded` objects carry type-specific extra fields (`increment` for
`WINDOW`, `code`/`message` for `RESET`) instead of a raw `payload_hex`, whichever is more legible for that
frame type.

`check-fixtures.mjs` validates that `hex` is even-length lowercase `[0-9a-f]*` **before** attempting to
decode it — `Buffer.from(hex, "hex")` silently drops trailing garbage instead of failing, which would hide a
malformed fixture rather than catch it.

Two fixtures are worth reading closely because they contradict a plausible-but-wrong guess about the wire
format: `unknown_frame_type.json` and `reserved_bytes_nonzero.json` are both `valid: true` — WIRE.md
section 2.2 says an unknown frame `type` is "ignore and count", and non-zero `reserved` bytes "MUST be
ignored (not rejected)". Similarly `data_on_stream_zero.json` is `valid: true`: stream-0 `DATA` frames are
exactly how the control channel itself is carried; only `OPEN`/`CLOSE`/`RESET`/`WINDOW` are illegal on
stream 0 (see `open_on_stream_zero.json`, `window_on_stream_zero.json`, `reset_on_stream_zero.json` for the
three that ARE illegal there).

Other notable cases: `window_high_bit_increment.json` is a `WINDOW` increment with its high bit set, i.e. one
that would push the sender's window past `2^31-1` — WIRE.md section 2.6 decision 1 makes this connection-
fatal `FLOW_CONTROL_ERROR`, and the checker's decoder implements the check (not just the fixture assertion).
`stream_zero_payload_over_16kib.json` is a stream-0 `DATA` frame one byte over the 16 KiB control-channel
limit (WIRE.md section 2.4) → `ENHANCE_YOUR_CALM`. `close_with_trailing_bytes.json` and
`close_nonzero_flags.json` are both `valid: true` (trailing bytes on `CLOSE` and non-v1 flag bits are both
ignored, not rejected, per WIRE.md section 2.2/2.3). `header_too_short.json` (7 bytes) and
`header_too_short_zero_bytes.json` (0 bytes) cover both ends of "shorter than the 8-byte header".
`reset_emoji_message.json` is a `RESET` message containing a valid multi-byte UTF-8 sequence (an emoji) —
decodes cleanly. `reset_nul_in_message.json` decodes cleanly too (a NUL byte is valid UTF-8 at the wire-frame
level) but carries a `policy_violation` note: WIRE.md section 2.3's "no NUL" is a SHOULD, not a wire
MUST, so rejecting it is SDK-level policy, not something this frame decoder enforces. The WS-level close
*reason* truncation rule (≤123 UTF-8 bytes, truncated on a character boundary, WIRE.md section 2.4) has
no fixture here on purpose — it's a property of the outer WebSocket close frame, not of this repo's 8-byte
mux frame format, so it's exercised as an SDK unit test, not a `spec/fixtures/frames/*.json` case.

## Sequence fixtures

`spec/fixtures/sequences/*.json` — behavioural transcripts for state-machine bugs that no single-message
schema check can catch (a wrong state machine, not a malformed message):

```json
{
  "description": "...",
  "role": "server",
  "steps": [
    { "recv": { "...": "a control message object (has t) or a frame object (has type)" } },
    { "send": { "...": "same shape" } },
    { "wait_ms": 5000 },
    { "expect": { "error_code": "...", "close_code": 4012, "stream_state": "closed" } }
  ]
}
```

Convention: `role` names which implementation-under-test perspective the transcript is written from
(`"server"` or `"client"`). Every step has **exactly one** of `recv`/`send`/`wait_ms`/`expect` —
`check-fixtures.mjs` enforces this. `recv` means a message/frame arrives *at* that role; `send` means that
role transmits it. A step's payload is either a control message object (identified by having a `t` field) or
a decoded frame object (identified by having a `type` field, one of `OPEN`/`DATA`/`WINDOW`/`CLOSE`/`RESET`);
frame payload bytes are given as `payload_hex` when the exact bytes matter, or `payload_length` when only
the byte count matters (flow-control scenarios). `wait_ms` advances a virtual clock by that many
milliseconds with no I/O, for timeout scenarios; the dead-peer sequence uses `wait_ms: 90001`, not `90000`,
because the keepalive watchdog fires once elapsed time since `last_pong_received` *strictly exceeds*
`ping_timeout` (WIRE.md section 2.9), i.e. at 90001 ms of silence, not at exactly 90000 ms.

Every `recv`/`send` control-message payload whose `t` is one of the 7 known types (`hello`, `welcome`,
`ping`, `pong`, `drain`, `error`, `app`) must validate against `control.relaxed.schema.json` —
`check-fixtures.mjs` enforces this too. Two escape hatches exist for sequences that deliberately exercise a
payload the schema itself would also reject: a payload whose `t` is not one of the 7 known types (e.g.
`unknown_control_message_type.json`'s `"t":"regsiter"`) is skipped automatically, since by definition it
matches no `$defs` entry; a step can also be marked `"schema_exempt": true` alongside its `recv`/`send` key
to opt a known-`t` payload out of the check on purpose — used by `hello_version_mismatch.json`, whose whole
point is a `hello.v` that fails schema validation (the protocol reports this as `UNSUPPORTED`, a semantic
rule layered on top of, not replacing, schema validity).

`expect` is a final-state assertion: any of `error_code`, `close_code`, `stream_state` (per-stream, when a
`stream_id` is implied by the preceding steps), `stream_reset_code`, and other implementation-observable
state (e.g. `send_window`) may appear; a harness should assert only the keys present, not enumerate every
possible field. `error_code`/`close_code`/`stream_state` explicitly set to `null` asserts the *absence* of an
error/close — i.e. the sequence must still be alive and healthy at that point.

Sequence ping ids are the sender's own counter, which starts at 0: fixtures scripting a `ping`/`pong`
exchange must use 0-based ids to match what a real implementation actually sends.

`error_code` is for a **connection-level** `error{code}` message (WIRE.md section 2.7/2.8) — it is
always paired with a `close_code`, and `check-fixtures.mjs` asserts `close_code == 4000 + <the error_code's
numeric value>` (or `1000` for `NO_ERROR`), per WIRE.md section 2.8's mechanical rule. `stream_reset_code`
is the distinct key for a **stream-level** `RESET(code)` (no accompanying WS close — the connection lives
on) — see `max_streams_exceeded.json`, where the client resets one offending stream with `STREAM_LIMIT`
while the connection itself stays up. Both `error_code` and `stream_reset_code` must be a real name from
WIRE.md section 2.8's table; `check-fixtures.mjs` checks both.

`role: "client"` fixtures script the mirror image of the (much larger) `role: "server"` corpus: every
`recv`/`send` is written from the CLIENT implementation's point of view, exercising the handful of
protocol violations only the client is ever positioned to catch — a server that (mis)opens an even or
out-of-order stream id, sends a WINDOW/OPEN/CLOSE/RESET on stream 0, floods the control channel, oversteps
a `drain{last_stream_id}` boundary, DATAs a stream past the client's own advertised window, or answers a
pong for an id the client never sent — plus the client-side halves of welcome validation (missing field,
version mismatch, `ping_interval` below the 5000ms floor, a second `welcome`) and keepalive (the client's
own pings going unanswered until `KEEPALIVE_TIMEOUT`). `reset_on_closed_stream_toward_client.json` and
`late_data_after_client_reset.json` intentionally use a RESET the *client itself* triggers (a stream-limit
refusal) rather than an application-driven reset, since a pure wire-level replay harness has no hook to
command an app-level stream write or reset; `window_exhaustion_then_resume_client.json` is written fully
protocol-correct for the same reason but is not fully drivable by every harness (see its own
`description`) — both are documented inline rather than silently adjusted to fit harness limitations.

## Consuming these fixtures from an SDK test harness

In any language: load every file under `fixtures/control/<type>/{valid,invalid}/`, feed `.message` through
your hand-written per-type validator/constructor, and assert the outcome matches `.wire_valid` — that is the
boolean a runtime validator should agree with (see "SDK runtime validators assert `wire_valid`" above); for
the schema cross-check described below, also assert `.message` against `control.schema.json` and
`control.relaxed.schema.json` and check they match `.schema_valid` / `.wire_valid` respectively. Load every
file under
`fixtures/frames/`, decode `.hex` through your frame parser, and assert the result matches `.decoded` (or
that parsing fails with `.expect.error_code` / `.expect.connection_fatal`). Load every file under
`fixtures/sequences/`, replay the `steps` against a real (or harness-simulated) connection from the given
`role`'s side, and assert every `expect` step holds at that point in the transcript.

**The rule that matters most:** `control.schema.json` is the cross-SDK conformance *oracle*, consulted only
by test suites (and by `tools/check-fixtures.mjs` in this repo). No SDK embeds a JSON Schema validator in
its production/runtime path. Each SDK's own hot-path validation is hand-written — a dispatch on `t`,
then explicit per-field checks — because that is what produces actionable error messages
(`welcome.ping_timeout (30000) must be at least 2x ping_interval (30000)` is not expressible in JSON Schema
at all) and because a spec whose whole pitch is "implementable in an afternoon" should not gain a runtime
dependency for message validation. An SDK's test suite should run every `control/` fixture through *both*
its hand-written validator and `control.schema.json`, and assert the two agree — that is where the schema
earns its keep, as the arbiter that keeps independent SDKs honest with each other.

## Validation

`spec/tools/check-fixtures.mjs` (Node built-ins only, no dependencies, no `package.json`) checks:

1. Every `fixtures/control/**/*.json`'s `schema_valid` matches what `control.schema.json` (strict) says
   about `.message`, and `wire_valid` matches what `control.relaxed.schema.json` (relaxed) says. Its `oneOf`
   is implemented correctly: **exactly one** `$defs` entry must match, not merely "at least one" — a message
   that satisfied two branches at once would previously have been accepted.
2. `control.relaxed.schema.json` is re-derived from `control.schema.json` on every run and compared,
   byte-for-byte, against the checked-in file; a stale generated file fails the build. Every fixture with
   `wire_valid: true` is also, as a consequence of (1), asserted to pass the relaxed schema.
3. Every `fixtures/sequences/*.json` file: `role` is `"server"` or `"client"`; every step has exactly one of
   `recv`/`send`/`wait_ms`/`expect`; every known-`t` control payload validates against
   `control.relaxed.schema.json` (see the escape hatches described above); every `close_code` paired with an
   `error_code` equals `4000 + <code>` (`1000` for `NO_ERROR`) per WIRE.md section 2.8; every
   `error_code`/`stream_reset_code` is a real name from that table.
4. Every `fixtures/frames/*.json`'s `hex` — first checked to be even-length lowercase `[0-9a-f]*` — re-decodes
   (per the section 2.2 header layout) to the header fields asserted in `decoded` (for the valid ones), or
   fails to parse for the stated structural reason (for the invalid ones the check can detect statically — a
   short header, an oversized message, a bad `WINDOW`/`RESET` payload length, a stream-0 payload over 16 KiB,
   or a `WINDOW` increment with the high bit set).
5. `fixtures/control/`, `fixtures/frames/`, and `fixtures/sequences/` all exist (hard failure, not a silent
   zero-fixture pass), every message type's `valid/`/`invalid/` pair exists (`envelope/` is exempt from
   needing `valid/`, see above), every type has ≥1 `schema_valid` fixture (except `envelope`) and ≥3 fixtures
   with `schema_valid: false`.
6. The total number of `*.json` files under `fixtures/` (excluding `fixtures/COUNTS.json` itself) is at least
   `fixtures/COUNTS.json`'s `minimum_total_fixtures` — a checked-in floor that must be bumped upward whenever
   fixtures are added, and must never be lowered to paper over a regression.

Run it with `node spec/tools/check-fixtures.mjs` from anywhere in the repo. Regenerate the relaxed schema
separately with `node spec/tools/gen-relaxed-schema.mjs` (or `--check` to only verify, no write).
